The register, as of 29 Oct 2026 (review 2 added SR-28 to SR-37). One row per risk the project knows about, whatever its state. Fixed means on the CLI's dev branch with a test that pins it; accepted means it stays, with the reason written down; open means a decision or a setting is still needed; designed means the launcher or a component will close it and nothing does today. The weight is the reviewer's judgement of what it would cost someone relying on the code as documented. A risk that is accepted is as much a part of this page as one that is fixed: the aim is that an outside review finds nothing here it has to tell the project.

How to read the states

StateMeaningWhere the proof is
fixedthe code refuses, closes or declares it; a test fails if it comes backtests/unit/test_security.py in the CLI, the test named in the row
acceptedit stays, because fixing it costs more than it buys at this stage, or because nothing below the launcher can close it; the reason is in the row and the code says so at run timethe row; the not covered line of run and hello
openneeds a person: a GitHub or PyPI setting, or a design decisionHardening §3; the roadmap
designedthe launcher or a component closes it; until then every row is a Boundary for a child and a Setting for whoever applied itPolicies §2

Risks the design carries, not the code

These are in the design pages already; they are repeated here so the register is one list.

#RiskWhere it is saidState
SD-01a policy a process applies to its own children is a Setting for that process: it could skip it. Every measured row today is of this kindPolicies §2; every hello rundesigned: the launcher above the agent
SD-02the hash the person supplies is only a boundary if the person obtained it independently of the agentThreat model §3documented; the mockup and the playground let the person compute it
SD-03v0 names ports, not hosts: any host on an allowed portPolicies §10designed: sharness.net
SD-04UDP is not seen by Landlock; without the namespace DNS resolvesExperiments E03designed: the namespace from the launcher; declared every run
SD-05RLIMIT_AS caps address space, not resident memory; the memory cgroup is the real wall and needs a writable cgroup treeContainment §1documented; declared when the cgroup could not be made
SD-06an unprivileged user namespace, used to get an empty network namespace without root, gives the child capabilities inside that namespace and widens the kernel surface it can reachrun.pyaccepted: the alternative is no namespace at all; the designed launcher runs as a separate uid and does not need it
SD-07a per-child cgroup that a lingering grandchild keeps alive is left for the kernel to freelimits.pyaccepted, low
SD-08/etc listed whole as readable includes files only root should read, when the child is rootthe example policiesdocumented; narrowing is in the advice
SD-09the example profiles list /etc as executable, which nothing needsexperiments/policies/accepted for now: changing a profile changes its pinned hash, quoted on this site; policy check advises against it; the next profile revision drops it
SD-10seccomp, per-component uids, the execute allowlist for the process tree, mutual TLS: the rows that make the containment claim strongest are not builtContainment §4designed; E05 to E08
SD-11root and the kernel are trusted; a kernel bug from inside a policy is out of scope; a microVM around the harness is the answerWhyout of scope, by decision
SD-12the chroot form of E09 runs the guest's binaries on the host kernel as root; it is a test bench, and now a pinned oneLinux in the browseraccepted: documented as needing root; the pins are SR-07

Adding to this page

A new finding gets the next SR- number and a row the day it is found, in whatever state it is in. A fixed row keeps its number for ever; nothing is deleted. The CLI's SECURITY.md points here, and every review on Reviews cites rows here.
