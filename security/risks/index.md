# Known risks

> **The register, as of 29 Oct 2026** (review 2 added SR-28 to SR-37). One row per risk the project knows about, whatever its state. *Fixed* means on the CLI's `dev` branch with a test that pins it; *accepted* means it stays, with the reason written down; *open* means a decision or a setting is still needed; *designed* means the launcher or a component will close it and nothing does today. The weight is the reviewer's judgement of what it would cost someone relying on the code as documented. A risk that is accepted is as much a part of this page as one that is fixed: the aim is that an outside review finds nothing here it has to tell the project.

## How to read the states

| State | Meaning | Where the proof is |
|---|---|---|
| **fixed** | the code refuses, closes or declares it; a test fails if it comes back | `tests/unit/test_security.py` in the CLI, the test named in the row |
| **accepted** | it stays, because fixing it costs more than it buys at this stage, or because nothing below the launcher can close it; the reason is in the row and the code says so at run time | the row; the `not covered` line of `run` and `hello` |
| **open** | needs a person: a GitHub or PyPI setting, or a design decision | [Hardening §3](../hardening/index.md#3-the-repositories-and-the-accounts-settings-only-a-person-can-change); the roadmap |
| **designed** | the launcher or a component closes it; until then every row is a Boundary for a child and a Setting for whoever applied it | [Policies §2](../../design/policies/index.md#2-who-enforces-decides-the-barrier-kind) |

## Risks the design carries, not the code

These are in the design pages already; they are repeated here so the register is one list.

| # | Risk | Where it is said | State |
|---|---|---|---|
| SD-01 | a policy a process applies to its own children is a Setting for that process: it could skip it. Every measured row today is of this kind | [Policies §2](../../design/policies/index.md#2-who-enforces-decides-the-barrier-kind); every `hello` run | **designed**: the launcher above the agent |
| SD-02 | the hash the person supplies is only a boundary if the person obtained it independently of the agent | [Threat model §3](../threat-model/index.md#3-the-two-trust-boundaries) | **documented**; the mockup and the playground let the person compute it |
| SD-03 | v0 names ports, not hosts: any host on an allowed port | [Policies §10](../../design/policies/index.md#10-a-v0-that-two-implementations-hash-the-same-runnable) | **designed**: `sharness.net` |
| SD-04 | UDP is not seen by Landlock; without the namespace DNS resolves | [Experiments E03](../../code/experiments/index.md) | **designed**: the namespace from the launcher; declared every run |
| SD-05 | `RLIMIT_AS` caps address space, not resident memory; the memory cgroup is the real wall and needs a writable cgroup tree | [Containment §1](../../design/containment/index.md#1-can-every-process-be-constrained-memory-included) | **documented**; declared when the cgroup could not be made |
| SD-06 | an unprivileged user namespace, used to get an empty network namespace without root, gives the child capabilities inside that namespace and widens the kernel surface it can reach | `run.py` | **accepted**: the alternative is no namespace at all; the designed launcher runs as a separate uid and does not need it |
| SD-07 | a per-child cgroup that a lingering grandchild keeps alive is left for the kernel to free | `limits.py` | **accepted**, low |
| SD-08 | `/etc` listed whole as readable includes files only root should read, when the child is root | the example policies | **documented**; narrowing is in the advice |
| SD-09 | the example profiles list `/etc` as executable, which nothing needs | `experiments/policies/` | **accepted for now**: changing a profile changes its pinned hash, quoted on this site; `policy check` advises against it; the next profile revision drops it |
| SD-10 | seccomp, per-component uids, the execute allowlist for the process tree, mutual TLS: the rows that make the containment claim strongest are not built | [Containment §4](../../design/containment/index.md#4-two-caveats-that-matter-more-than-the-kernel) | **designed**; E05 to E08 |
| SD-11 | root and the kernel are trusted; a kernel bug from inside a policy is out of scope; a microVM around the harness is the answer | [Why](../../design/why/index.md#threat-model) | **out of scope, by decision** |
| SD-12 | the chroot form of E09 runs the guest's binaries on the host kernel as root; it is a test bench, and now a pinned one | [Linux in the browser](../../code/browser/index.md) | **accepted**: documented as needing root; the pins are SR-07 |

## Adding to this page

A new finding gets the next `SR-` number and a row the day it is found, in whatever state it is in. A fixed row keeps its number for ever; nothing is deleted. The CLI's `SECURITY.md` points here, and every review on [Reviews](../reviews/index.md) cites rows here.
