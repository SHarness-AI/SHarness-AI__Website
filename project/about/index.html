By Dinis Cruz. Design session written up with Claude, 24 October 2026.

SHarness is unrelated to Sharness, the shell testing library derived from Git's test suite (felipec/sharness).

The name

SHarness is a secure harness: the layer agents run inside so that they run securely. It takes behaviour policies from text the agent reads to rules the agent runs inside, enforced from outside the agent's environment. Dinis Cruz's memo on the name and the direction is the article A secure harness for agents.

Naming rules

  • The brand is SHarness. Lower-case sharness appears only in code identifiers (sharness.kms, sharness_ai).
  • There is no plain sharness command: on Debian, pkgsrc and OpenBSD that name is the unrelated shell test library's package. The command is sharness-ai.
  • Environment variables use SHARNESS_AI_, not SHARNESS_, which the shell test library uses.
  • One role, one noun: each component is named for its one job.
  • The names are a tree, sharness.<door>.<target> (Dinis Cruz's rule of 26 Oct 2026, set out on the PBP on one page §6). A door is sharness.<resource>: fs, net, db, llm, bash, kms; the door alone is the API and the vocabulary its rows are written in, never a place. A target is where the door sends: sharness.fs.disk, sharness.fs.s3, sharness.net.direct, sharness.net.proxy, sharness.net.http, sharness.net.git, sharness.db.sqlite, sharness.db.postgres, sharness.llm.tools. Read from above, the dot means sits on: the parent closes every other path, so the child's only way to the world is through it. Read from below, it means sends to. Depth is open (sharness.net.http.gmail), and a level earns a name only when it adds nouns its parent cannot see; otherwise it is configuration of the parent.
  • .twin is a terminal suffix on any target: the thing named before it runs as a simulation of what is on the other side (sharness.fs.s3.twin, sharness.db.postgres.twin, sharness.fs.disk.twin). A door alone has no other side, so sharness.fs.twin is not a name; a twin's backend (memory, a vault, record and replay) is its configuration, not a name. The same tree names the identity (spiffe://<session>/fs/s3), the policy (extends, composed by intersection) and the code: sharness_ai.fs is the door's interface module, sharness_ai.fs.disk and sharness_ai.fs.s3 its targets, in the CLI for now and a distribution of its own (sharness-ai-fs-s3) when a target leaves it.
  • Withdrawn: dialect (the second level was briefly called a protocol; it is the target) and .memory as a name (memory is a twin's backend).

Where it came from

SHarness grew out of sgit, the encrypted vault CLI, and uses sgit's PKI. The first analysis was A vault key that never lands; the handover it builds on is pki.sgit.ai/handover.md; its policies apply the Agent Behaviour Policy model to processes. sgit is the first app designed to run inside SHarness.

What is real today

The name, this site, and a package with the first experiments. The sharness-ai package on PyPI (v0.1.0, as of 24 Oct 2026) reports its version and prints its help; its dev branch carries experiments E01 to E04 (probe, policy hash, run, hello), unreleased. No SHarness component is built. The status of every claim is on Evidence and What exists today.
