Status: design. Nothing is built. This page lists what is decided, what is open, and the first tasks for the agents that will build SHarness. Decisions below are dated as of 24 Oct 2026 unless marked otherwise.

Decided

DecidedWhy
Single-purpose components, one job each (sharness.<role>)the edges between them are the security model
Edges deny by default; the app never talks to the KMSthe app never sees keys; the KMS never sees the network or disk
Mutual TLS 1.3 everywhere, roles in certificate URI SANs, issued by a session CA whose key is destroyed after issuingthe same code local, Docker, Kubernetes, remote; ~3.2 ms per handshake, measured
The KMS never returns a clear key; it returns derived keys sealed to the caller's one-time keynothing between the KMS and the consumer sees plaintext, including the agent
The KMS makes its own private key; it never leavesone sealed place
Default key holding: frozen process + memfd_secret0.28 ms freeze / 0.13 ms thaw, measured; secret pages unreadable even through /proc/<pid>/mem
Policies are hashed (canonical JSON, SHA-256); the hash comes from the person or is signed by the root keyotherwise a prompt-injected agent could widen them
Host allowlisting is done by sharness.net as the TLS client, not by the kernelthe kernel only sees the platform proxy's port; .net sees and verifies the name
The command is sharness-ai, not plain sharness (decided 24 Oct 2026, after the design pack)sharness is the Debian / pkgsrc / OpenBSD package of the unrelated shell test library; sharness-ai matches the PyPI distribution
Build order: the ladder (decided 24 Oct 2026, from the memo): browser mockups, then experiments any session can run, then Linux experiments, then components, then the launcher above the agentstart small, each piece in isolation; see Mockups and experiments. E01 to E04 are runnable
A v0 policy of six keys that the CLI and the browser hash identically, enforced with Landlock, growing towards the full schematwo implementations, one hash, before layers and signing

Refactor path in sgit

sgit 0.24.0 reads the vault key directly in many places (the origin article counts 27 read sites in 17 files; a broad grep for _read_vault_key|load_vault_key|vault_key_path finds 65 references in 23 files, including imports). After derivation almost nothing needs the clear key except show-key, rekey and move.

StepChangeEffect
0Fix independently: private keys from pki keygen use PBKDF2 at 2,048 iterations (measured, 0x0800) → Argon2id; Secrets__Store fixed salt → per-user random saltremoves two weaknesses whatever else happens
1The door: one Key_Source interface ("vault id + derived keys for this folder"), reading vault_key today; lazy imports per subcommandno behaviour change; all call sites go through it; tests prove it
2Key_Source backed by the KMS protocol; clone --sealed, vault_key.sealed, vault seal-local, vault seal --to; .net filters traffic; the app receives derived keys sealed to its own one-time keykey never on disk, argv or stdout
3Full split: vault crypto and server I/O move into .net; the app asks for operations, not keysthe app holds no keys and has no network
4.fs as the only writer; then optionally FUSEbusiness rules on disk enforced outside the app
5P-256 ECDH envelope for hardware keys (TPM / PIV / Secure Enclave); commit signing with the identityhardware-backed KMS

End state: the platform provides it

The local KMS process and a Lambda are stand-ins. The right owner of the KMS and of policy enforcement is the agent execution environment: it already knows which session is calling (which solves caller authentication for an ephemeral container), it already sits outside the container, and it can bind key lifetime to session lifetime and keep decrypted results out of transcripts and logs. The protocol is designed so that apps don't change when the KMS moves from a local uid to a Lambda to a platform service.

This is a proposal for what platforms should offer. No such service is known to exist today, and nothing on this site describes any platform's plans.

For the agents that will build this

Read in order: the design pack README, then documents 01 to 07 (all on The source documents). Documents 01–04 use sgit-specific names: sgit-kms → sharness.kms, sgit-net → sharness.net, sgit-fs → sharness.fs, sgit-cli → the harnessed app.

Ground rules carried from the design:

  • Status words matter. Say measured only with a method and a date; everything else is designed or proposed. Never claim anything is built or released before it is.
  • The threat model trusts the kernel. Never claim protection against root or kernel compromise.
  • Components small enough to read in one sitting: launcher ≤ 400 lines, each component ≤ 300, a shared library ≤ 400 (proposed targets).
  • Reuse before building: Landlock, seccomp, namespaces, cgroups, stdlib ssl, JSON Schema, strace, memfd_secret.
  • Testing inside a live agent session follows the safety rules on Enforcing the process tree: never touch the orchestrator, never firewall uid 0 or the model API, run experiments as child subtrees, clean up.
  • Publish results here: every new measurement goes on Evidence with its method and date.

Source: 00-README §5–6, 01-architecture §7, and the brief for this site §7.
