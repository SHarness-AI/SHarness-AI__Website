sharness.ai / admin

How this site is built

Hand-written static HTML with no framework and no build step, plus a handful of small tools that keep it consistent. Modelled on the *.sgit.ai sites (nfrs.sgit.ai in particular), using the same pipeline and gate. The conventions are documented at coding.sgit.ai.

The tools

FileJob
admin/build/version.txtOwns the site version. Bumped exactly once per release.
admin/build/chrome.pyThe single definition of the nav, the footer and the version badge, rewritten in place across every page. Also stamps the version into llms.txt and index.md.
admin/build/validate.jsThe pre-release gate: version agreement, internal links, canonical host against CNAME, a vault-key-shaped-string tripwire, and generate or date every number. Any failure stops the release.
admin/build/gen_sitemap.pyWrites sitemap.xml from the tree, with each page's last commit date.
admin/build/gen_llms_full.pyWrites llms-full.txt: the agent surface in one fetch.

The pipeline

.github/workflows/deploy-pages.yml, in this order:

  1. validate: runs the gate. It also runs on pull requests, so branch work is gated before it reaches the release branch.
  2. tag-release: every push to dev is a release. The version in version.txt must match the release commit's subject (site vX.Y.Z: ...), and must be the next minor or a deliberate major bump. CI then tags the release commit.
  3. deploy: publishes the tree to GitHub Pages. A push to main, or a manual run, deploys without tagging. Never runs when validation failed.

Cutting a release

# 1. bump admin/build/version.txt, add a row to admin/versions.html
python3 admin/build/chrome.py
python3 admin/build/gen_sitemap.py && python3 admin/build/gen_llms_full.py
node admin/build/validate.js
git commit -am "site vX.Y.Z: ..." && git push origin dev
