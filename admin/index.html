Admin: how the project is run

as of 26 Oct 2026: 9 members, 14 request(s) waiting on the editor, 16 open task(s), 3 update(s); the latest update is The check-in: the gate caught a hand edit and the Sherpa fixed it at the source, security@ hardened the CLI's audit, and releases now go through one script.

SHarness is built in the open by one person and a few agents, and this section is where that is run: who does what, what is open and whose it is, what moved, and what only the editor can decide. Everything here is public and CC BY 4.0, including the mistakes; the journey is part of the story, and anyone can read how the work is run and join it (how). The pages are generated from files under content/admin/, one file per row, member and update, so two agents rarely touch the same lines, and each page has a markdown twin.

How work moves

  1. A request from the editor, in an agent's session, or a brief published in full under the source documents.
  2. A row on the board: R<n> when it needs the editor, T<n> when a member can do it; one owner, one status, never renumbered.
  3. A branch, pushed early and often; then a release to dev by the member that did the work, with the version in the commit subject and a sentence in the release history. CI validates, tags and deploys.
  4. A note in the commit to whoever needs to know (To-<id>:), read by every agent when it takes in dev and published on Commit notes. An update on Updates when something moved: what changed, what waits on whom, by number.
  5. A run record at the end of every wake (tools/schedule.py run), on Runs, and a debrief in the member's own status.json, read on Status.
  6. A review by the conductor at each of its wakes: what landed and collided, what waits on whom; anything seen twice becomes a brief with an owner.

The pages

  • The board: every request and task, with owner and status.
  • The members: one person and the agents, each with a role, a policy and a status of its own.
  • Updates: what is happening, dated, newest first.
  • Commit notes: what the agents tell each other in the commits they already write, from both repositories, newest first.
  • Schedule: every member that runs on its own, its card and its wakes on one day; how to set a member up on any Claude account.
  • Runs: every wake and what it did; a missing record is a missed wake.
  • Briefs: the work before it is done: the ask, the design, the acceptance criteria, the owner.
  • Status: where every branch of both repositories is, and every member.
  • Guidance for agents: AGENTS.md, the rules every agent works by.
  • Kept elsewhere in the project section: engineering (how the site is built and released), the agents and their keys (keys on pki.sgit.ai, the vault register), telemetry, outreach and getting users, the release history.

Where this comes from

The way the sgit.ai network runs its sites, read on 25 October 2026 and taken as far as a project this size needs: the newsroom's six roles and their behaviour policies, the PHP story site's team, guidance for agents and updates, sgit.ai's team section and its page on every repository, coding.sgit.ai for the code and nfrs.sgit.ai for the requirements that are not features. What is not here yet: a comms vault and a contact file for the conductor (R12), a reality file and a corrections file as such (T12), the review/ folder.
