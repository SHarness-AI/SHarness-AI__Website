sharness.kms: the only place a secret lives

Status: designed, with the protocol written and the handover measured by hand. Not built. Written as of 25 Oct 2026.

Its one job

Open a sealed message addressed to its identity, check it, derive the keys the caller needs, and re-seal them to a key the caller made for this one request. It never returns a clear key. It holds the session identity's private key, made inside it and never exported, in a memfd_secret page, and it is frozen by the launcher between calls.

The API (proposed; the protocol is on Keys and the KMS §3)

Answers sharness.net and sharness.llm only: the edge list has no other caller, and the app can never reach it.

RequestBodyResponse
POST /v0/unwrap{"v": 1, "sealed": "m1.…", "eph_pub": "<P-256 SPKI>", "op": "read", "vault_id": "…", "nonce": "…", "expires_in": 300}{"v": 1, "sealed_to_eph": "<envelope>", "expires_in": 300}: the derived keys, sealed to the caller's one-time key; the vault key itself never leaves
POST /v0/seal_to{"sealed": "m1.…", "recipient_k1": "…", "expires": "…", "op": "read"}{"m1": "…"}: the key re-sealed to another identity without ever being in clear outside the KMS (sgit vault seal --to)
GET /v0/identitythe public bundle k1 (record and encryption fingerprints); the only thing it ever prints
GET /v0/policyits own policy and hash

Requests, and their verdicts (designed)

Who asks whatVerdictBy
.net asks unwrap for a vault with op=read, a fresh nonce, a sealed key addressed to this identitythe read key, sealed to the caller's one-time key; the nonce recorded.kms
the same nonce a second timerefused: replay.kms
unwrap of a message sealed to a different identityrefused: not addressed to me.kms
unwrap of a message whose sender does not chain to the pinned rootrefused.kms
.net asks op=write where the policy binds writes to a fresh approvalheld until the person approves, then answeredpolicy, then .kms
the app, or bash, or any process but .net and .llm, opens a connectionthe TLS handshake fails: the role is not in the edge listthe session CA and the edge list
anything reads /proc/<kms pid>/memEPERM: a different uid, and the page is memfd_secret, unreadable even by rootthe kernel
anything asks for the private keythere is no such requestthe design

What it enforces, with what
Files and networknone: Landlock with no filesystem rights after start; an empty network namespace; it answers on loopback only
Memorythe private key in a memfd_secret page: measured unreadable even by root (24 Oct 2026)
Lifetimefrozen between requests by the launcher: thaw, answer, freeze; 0.13 ms and 0.28 ms measured
The envelopeECDH P-256 to the caller's ephemeral key, HKDF-SHA256, AES-256-GCM with the request hash as associated data; a copied response is useless, the ephemeral key existed for milliseconds
Remotethe same protocol against a cloud KMS or an HSM, with the caller bound by its certificate (§6)

On its own

Adopt only this component and a secret handed to an agent is never in clear on disk, on a command line, or in the transcript: it arrives sealed to the KMS's identity, and what comes out is sealed to a key that lives for one request. The agent sees a fingerprint and a status line. The sealed handover is the worked example, and the gap it closes is the one SHarness started from (Why).

What it does not do

It does not decide what the derived keys are used for once sealed to the caller: that is the caller's policy, which is why op=read returns only the read key. It does not protect against root reading the page: it does, by memfd_secret, but against a compromised kernel nothing here holds, and the site says so.

Sources: Keys and the KMS, Components. Measurements: Evidence §3 and §6.
