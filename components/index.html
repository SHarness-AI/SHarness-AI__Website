The components: the operating system a process sees

Status: design, with two halves runnable. Six components, one job each, proposed and not built; the kernel locks under them are runnable today (sharness-ai run) and the network allowlist outside a process is a working prototype in the playground. This page is the components as a user would meet them: the only doors a process has, each a small REST service on loopback, each worth adopting on its own. Written as of 25 Oct 2026.

1. Why "an operating system"

Ask what a process can do at all and the list is short: files, the network, other processes, memory, its identity, the model it talks to, the secrets it needs (the whole surface). SHarness bounds each in the kernel where the kernel can (Landlock, namespaces, seccomp, cgroups, one uid per process) and puts a component where it cannot: the kernel can refuse a connect(), but it cannot say which hostname is allowed; it can refuse a write(), but not that the bytes are a clear key. So a process in the harness has no filesystem of its own to write, no network stack of its own, no key store, no shell, no model API. It has five doors, and each door is a small service with a policy, a port and a certificate. That is an operating system for one process: it contains exactly what the policy lists, and nothing else.

the filesystem, to writea service that writes under rules, and refuses clear keyssharness.fs

2. Everything is a request

Every door speaks the same way: a small REST API over a loopback TCP port, under mutual TLS from a session CA, one certificate per role, and an edge list that says which role may call which (Architecture). A request is a JSON body; a verdict is a status code and a reason. That has three consequences a user feels at once:

  • Any language can call a door. A harness-aware app, an MCP server, a shell script with curl and a client certificate: the protocol is HTTP.
  • Every door can be watched. A request that was refused says why, and a log of requests is a log of what the agent tried. The playground's network panel is this for one door, in a browser.
  • The cost is small, and measured. A mutual TLS handshake between two local processes took about 3.2 ms, a 600-byte round trip under a millisecond, and the three handshakes of an sgit command about 10 ms, against 146 ms the command already spends importing Python (Evidence §6, 24 Oct 2026). Loopback is not where the time goes.

Each component page shows its requests: what is asked, what is allowed, what is refused and by which layer. The clickable edge matrix shows which layer refuses a call between any two roles.

3. Pick one

The components are designed to run together under one manifest hash, and that is the reference implementation. They are also designed so that one of them, alone, is worth having:

Just this oneWhat you get on day oneWho wants it
sharness.netan inline proxy that is the TLS client for everything the agent reaches, with a hostname allowlist, no redirects to other hosts, no IP literals, and a log of every request; the model API traffic includedanyone running an agent that must not talk to the wrong host
sharness.bashevery shell command the agent runs in a fresh sandbox under a named profile, output filtered for secretsanyone whose agent runs commands
sharness.llmthe model API key out of the agent's process; a pinned tool list; a secret filter on every tool result before the model sees itanyone whose agent holds an API key in an env var
sharness.kmssecrets that are never in clear anywhere a transcript can seeanyone handing keys to an agent
sharness.fswrites under rules, and a refusal to store anything that parses as a keyanyone whose agent writes into a repository

Adopting one door does not bind the agent itself: that is the launcher's job, and the caveat on every page here. It does bind everything that goes through the door, which is where most of the damage an injected agent can do goes through.

4. Where to start: bash

The first component to build is sharness.bash, because it is where the others are decided. A shell command is free text; no schema bounds its intent, so the only enforcement is on what the process can do, and that is exactly the set of locks every other component also needs: its own uid, no capabilities, no_new_privs, a pid namespace, a pids cgroup, Landlock on the workspace with no execute right, network none or through .net only, seccomp. sharness-ai run is the one-process form of that today, measured on three kernels; sharness.bash is the same locks behind a request, applied by a server outside the agent's domain so the agent cannot skip them (the process tree). Once a command can only run through that door, the other doors are the only ways out of it.
