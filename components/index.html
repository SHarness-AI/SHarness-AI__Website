Components

Status: design. Every component below is proposed; none is built. Measured figures are as of 24 Oct 2026, in one Claude agent workspace.

Where the components sit and which may talk to which is on Architecture.

The harnessed app (for sgit: its CLI)
Jobparse the user's command, call sharness.fs and sharness.net, render output
Holdsno key of any kind; sees file contents (it must, to show diffs)
Talks to.fs and .net only
Filesread-only on the clone folder; writes nothing (every write goes through .fs)
Networknone: a network namespace with only loopback, or Landlock network rules allowing only the .fs and .net ports
Lockdownits own uid, all capabilities dropped, no_new_privs, RLIMIT_NPROC=0, Landlock, a seccomp allowlist
Refusesshow-key on a sealed clone without --reveal; any plain vault key on argv (all 14 sgit commands that take one)

An agent loop such as Claude Code is the same role for agents: it routes, and runs nothing itself (see Agents and LLMs).

sharness.launcher

Runs outside every domain. In order:

  1. Read the policy manifest, compute its hash, and refuse to continue unless it matches the hash the person supplied or the manifest carries a valid signature from the root key.
  2. Create one ephemeral uid per component (measured: user + firewall rule + locked launch + teardown ≈ 49 ms).
  3. Create the session CA and the role certificates; destroy the CA key; record the CA certificate hash.
  4. Start sharness.kms; it makes the session identity and prints only the public bundle (k1); freeze it.
  5. Per command, start the other components under their policies (new namespaces ≈ 4 ms, measured), let them run, tear them down.
  6. At session end, thaw and kill sharness.kms; delete users, firewall rules and sockets.

Who runs the launcher decides what the locks are. If the agent runs it inside its own session, the locks are a Boundary for everything the agent starts but only a Setting for the agent itself (in the measured environment the agent is root and could undo them). A script that starts the agent makes them a Boundary for the agent; the platform running the launcher makes them a Boundary all the way down.

sharness.kms
Jobopen a sealed message addressed to its identity, check it, derive keys, re-seal them to the caller's one-time key
Holdsthe session identity's private key (made inside, never exported); the nonce record
Answerssharness.net and sharness.llm only
Files / networknone (Landlock with no filesystem rights after start; empty network namespace)
Lifetimefrozen between requests: thaw → answer → freeze (0.13 ms / 0.28 ms, measured)

It never returns a clear key. Protocol and key lifetime: Keys and the KMS.

sharness.net
Jobevery byte to and from the outside; the KMS client; (in the full split) all vault encryption, decryption and signing
Holdsderived read/write keys for one command, in a memfd_secret page; never the vault key
Business ruleshost allowlist; endpoint allowlist; vault-id allowlist; read-only vs read-write per policy; no redirects to other hosts; IP literals refused
Why it is the TLS clientthe kernel only sees 127.0.0.1:<proxy port>. sharness.net sends CONNECT host:443, sets SNI and Host, and verifies the certificate for that name. A pure relay would let the inner process choose SNI and Host (domain fronting)

sharness.fs
Jobapply writes to protected folders (for sgit: the working tree and .sg_vault/) under rules
Holdsno keys; talks to nobody, only answers the app
Business ruleswrites only under the root it owns; no symlink or .. escapes; in .sg_vault/local/ accepts only sealed formats and refuses anything that parses as a clear vault key, a PEM private key or a bearer token; strips exec bits unless policy allows; size and count limits
Implementationfirst, a process owning the folder (other uids have no write permission); later, possibly a FUSE mount enforcing the same rules for any tool. Which one is an open decision

sharness.bash

Bash is the escape hatch from every other component: while the model can run any command as root with network, the policies on .fs, .net and .kms mean little. A command is free text, so no schema can bound its intent; enforcement is on what the process can do.

LockSetting (proposed)
uidone ephemeral uid per session, never root
pid namespacecannot see or signal the harness or any component
process countpids cgroup limit (e.g. 64), not RLIMIT_NPROC=0: a shell must fork
filesLandlock: workspace per profile; /usr read-only; no other component's folders or sockets; the workspace has no execute right
networknone by default; when allowed, only via sharness.net
seccompdeny ptrace, mount, keyctl, bpf, unshare, execveat, … (seccomp not yet measured)
outputstdout and stderr pass the same secret filter before becoming a tool result

Profiles are chosen by policy and requested by the model: analyse (workspace read-only, no network), build (read-write, package registries and GitHub via .net), admin (fresh approval from the person each time). Making Bash impossible to skip is Enforcing the process tree.

sharness.llm

A Messages API endpoint with a Process Behaviour Policy, sitting where ANTHROPIC_BASE_URL points. It checks the request (model allowlist, pinned tools list, token budget), filters every tool result and user message for secrets, adds the real API key (obtained sealed from .kms), forwards, and streams the response back unchanged. Details on Agents and LLMs.

sharness.policy

Not a process: the manifest, one entry per component, composed by intersection and hashed. The hash the person supplies covers everything, including the session CA certificate and the code hash of every component. See Process Behaviour Policies.

Two ways for an app to be compatible

Running an unmodified app in the harness breaks it: it tries to write where it may not, connect where it may not, read keys that are not there.

Transparent (no app changes). The harness presents ordinary interfaces backed by its components:

App expectsHarness presents
a writable foldera bind mount or FUSE mount served by sharness.fs
the internetHTTPS_PROXY pointing at sharness.net (CONNECT with host allowlist)
a model APIANTHROPIC_BASE_URL pointing at sharness.llm
a shellsharness.bash as an MCP server, or a one-line hook rewriting to its client
a secret in an env var or filenothing: this is the case transparency cannot cover safely

Harness-aware (small app changes) for what transparency can't do, mostly secrets. For sgit: one key-source interface backed by sharness.kms; clone --sealed, vault_key.sealed, vault seal --to, plain keys refused on argv; later, vault crypto and server I/O move into sharness.net.

The rule: an app needs harness awareness only where it handles secrets or where a policy must understand its protocol. Everything else is transparent.

As little code as possible

Most of the harness is configuration of things Linux and Python already have:

NeedUseNot
process isolationuids, setpriv, namespaces, Landlock, seccomp, cgroupsa custom sandbox
transport and identitystdlib ssl, cryptography for the session CAa custom protocol or a mesh
schemasJSON Schema (and MCP inputSchema for tools)hand-written validators
policycanonical JSON + SHA-256 + an existing signature (sgit PKI)a policy language
tracing a policystracea tracer
secret storagememfd_secret, cgroup freezer, kernel keyringan HSM emulator

Size targets (proposed): launcher ≤ 400 lines; each component ≤ 300; a shared library (Landlock, mutual TLS, framing, schema check) ≤ 400. Components must be small enough to read in one sitting; that is part of their security.
