# sharness.ai — the SHarness-AI website

The home of the SHarness-AI project and its command line tool, `sharness-ai`
([PyPI: `sharness-ai`](https://pypi.org/project/sharness-ai/),
[source](https://github.com/SHarness-AI/SHarness-AI__CLI)).

Live site: https://sharness.ai (GitHub Pages, deployed from `dev`).

Built the same way as the *.sgit.ai sites (modelled on
[SGit-AI__Website__NFRs](https://github.com/SGit-AI/SGit-AI__Website__NFRs)): hand-written
static HTML, no framework, no build step, a pre-release gate, and validate → tag → deploy.

## Structure

Five sections, each with an `index.md` hub, plus the articles and the files agents read. Markdown
is the source of every page that has a twin; the HTML beside it is generated and never edited.

| Folder | What | Source of truth |
|---|---|---|
| `design/` | the brief (the section's index) and the design pages: why, architecture, components, keys, policies, agents, process-tree, surface, containment, spectrum, roadmap | `index.md` in each, rendered by `tools/gen_pages.py` |
| `code/` | where the code is, the CLI, experiments, flows, examples, languages | same |
| `evidence/` | measurements (the index), status, the research note, the market analysis | same |
| `explain/` | the hub, `storyboards/` (generated from `content/storyboards/`), `mockups/` (hand-written HTML) | `content/storyboards/` and the mockups' HTML |
| `articles/` | the articles in the newsroom's format, generated from `content/articles/`, and their lead figures | `content/articles/` |
| `security/` | the project's own account of its security: the hub, threat model, known risks (the register), reviews, hardening, supply chain | `index.md` in each, rendered by `tools/gen_pages.py` |
| `code/releases/` | the `sharness-ai` code at immutable paths (`vN/vN.M/vN.M.P/`, complete, with `manifest.json`), `releases.json`, `latest.json`, `latest/`, and the `dev/` snapshot | `tools/releases.py` (`cut`, `snapshot`, `check`, `live-check`); never edited by hand |
| `admin/` | how the project is run: the hub, `board/`, `members/` (one page per member), `updates/` (one per update), `notes/` (the commit notes of both repositories), `schedule/` (every member's card), `runs/`, `briefs/`, `guidance/` (AGENTS.md rendered), `status/` | generated by `tools/gen_admin.py` from `content/admin/` and `AGENTS.md`; never edited |
| `project/` | about, `sources/` (the design pack and memos, verbatim), `agents/`, `outreach/`, `telemetry/`, `engineering.html`, `comms.html`, `releases.html` | markdown pages rendered by `tools/gen_pages.py`; `engineering.html` and `releases.html` hand-written, `comms.html` generated from the board's rows; the pack is never edited |
| `data/` | `telemetry.json`: the telemetry lane's write-only credential and public key (publishable by design); `telemetry-report.json` once the first drain runs | written by `tools/telemetry_postmaster.py` and `tools/telemetry_drain.py` |
| `assets/` | `site.css`, `nav.js`, `telemetry.js` (one anonymous event per page, see `/project/telemetry/`), `images/` | |
| `content/` | the sources the generators read: `articles/`, `storyboards/`, `admin/` (`board/<ID>.md`, `members/<id>/` with `ROLE.md`, `policy.json`, `status.json`, `card.json`, `updates/<id>.md`, `briefs/<date>__brief__<slug>.md`, `runs/<id>/<time>.json`, `status.json`) | |
| root | `WAKE.md`: what every scheduled wake does; `AGENTS.md`: the guidance every agent reads, on both repositories (rendered at `/admin/guidance/`); section 6 is Commit-FS-lite, how the agents talk in their commits; `tools/notes.py <id>` prints the notes to a member | kept by the conductor |

| `tools/` | `release.py` (the bump CI performs), `chrome.py` (nav, footer, badge), the generators, `releases.py` (the immutable releases of the code), `validate.js` and `validate_storyboards.cjs` (the gate) | |
| root | `index.html` and `index.md`, `404.html` (maps the pre-v0.5.2 addresses to the new ones), `llms.txt`, `llms-full.txt`, `sitemap.xml`, `robots.txt`, `CNAME` | |

## Release process

CI owns the version (R23, 26 Oct 2026; the scheme of the send repository). Nobody writes `/version`
by hand; the deploy workflow refuses a push that does.

1. Work on a branch of your own. When a step is finished:
   `RELEASE_TRAILER=$'Agent: <id>' python3 tools/ship.py "what changed" [--body-file F] [--snapshot]`.
   It commits the work with your subject, body and trailers, merges `dev`, runs `chrome.py` and
   every generator, the gate and every `--check`, pushes to `dev`, and waits for CI.
2. Every push to `dev` runs `.github/workflows/deploy-pages.yml`: validate → **release** → deploy.
   The release job reads the tags, takes the next number (`dev`: the last number plus one;
   `main`: the middle number plus one, the last to zero), runs `tools/release.py`, which writes
   `/version`, adds the row to `project/releases.html`, re-stamps every page and runs the gate again;
   CI commits that as "site vX.Y.Z: <your subject>", tags the commit, pushes branch and tag, and
   deploys that commit. A push that lands while the job runs rides the same release; no number is
   ever guessed, and no release is ever left untagged.
3. To cut a minor: push `main` (fast-forwarded to `dev`, or `dev` merged into it). CI numbers it
   `vX.Y+1.0` on `main` and fast-forwards `dev` to it when it can. The next push to `dev` is
   `vX.Y+1.1`. Pull requests run validation only.
