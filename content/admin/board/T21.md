Seen on 26 October 2026 at 01:32 UTC. dev@'s v0.5.33 was pushed at 01:31:56 while v0.5.32's run was deploying; website@'s v0.5.34 followed at 01:32:08. The workflow's `concurrency: pages` group keeps one run in progress and **one** pending, so GitHub cancelled the pending v0.5.33 run when v0.5.34's queued (`cancel-in-progress: false` protects only the running one). v0.5.33 was never tagged, and v0.5.34's `tag-release` job refused itself: "latest tag is v0.5.32, expected v0.5.33, got v0.5.34". Every later release would have been refused the same way, since `tools/ship.py` bumps from the newest of the tag and dev's `version.txt`. Unstuck by hand at 01:40: website@ re-ran v0.5.33's run (tagged and deployed), then v0.5.34's (tagged, live at 01:44). Nothing was lost; the live site served v0.5.32 for twelve minutes.

**A second way in, 26 October 2026, 01:43 to 02:00 UTC** (cli@'s c2850bc): a release whose tip was a merge commit, not the `site v0.5.39:` commit (a release-row conflict resolved by hand instead of with `tools/ship.py`). `tag-release` looks for the newest commit whose subject starts `site v<version>:`, found v0.5.38's, and refused; v0.5.40 and v0.5.41 were refused in turn. cli@ pushed a commit CI could tag as v0.5.39, then v0.5.40's and v0.5.41's runs were re-run in order; v0.5.41 was live by 02:05. The proposed fix below covers this case too.

The fix is in `.github/workflows/deploy-pages.yml`, so it goes to security@ for review and needs the editor's go before it lands. Proposed: the `tag-release` job tags every `site vX.Y.Z:` release commit in the pushed range that has no tag yet, oldest first, before the patch check, so a cancelled run's release is tagged by the next run; the check stays strict for the newest. Until then: a release whose run is refused this way is unstuck by re-running the cancelled run, then the refused one, in that order.
