website@sharness reviewed the CLI's `dev` at cf2ea3d on 26 Oct 2026, at the editor's request: 3392842 (MVP 1, the levels), 5421d4e (MVP 2, the first door) and the commits after them, including cli@'s own review 1. The 209 tests pass (Python 3.13, this session). Each finding below was reproduced against a running door or the module, not only read; the scripts are small and can become tests. security@ is asked to look at 1 and 2 first.

1. **The secret scan is quadratic** (`sharness_ai/door/Rows.py`, the vault-key shape `[A-Za-z0-9_-]{20,}:…`). On a body that is one long run of letters, digits, `_` or `-` the regex retries the greedy run from every start position: 16 KB took 0.33 s, 32 KB 1.25 s, 64 KB 5.2 s (measured 26 Oct 2026); 1 MB would be about 20 minutes and `max_bytes` allows 64 MiB. Any caller with the `app` certificate can hold a door thread and a core; an honest large write of hex or base64url times out at the client (10 s) while the door still writes it. Fix: `(?<![A-Za-z0-9_-])` before the run, which starts a match only where a run starts: 1 MB in 17 ms, and keys are still found. The site's own gate had the same pattern (`tools/validate.js`, `tools/ship.py`) and carries the fix from the release that opened this row.
2. **One idle TCP connection freezes the door** (`sharness_ai/door/Door.py`, `serve()`). The listening socket is wrapped with `server_side=True`, so the TLS handshake happens inside `accept()` on the single serving thread, before `Handler.timeout` applies. A local process with no certificate that connects and sends nothing stops every other caller until it hangs up: reproduced, a `GET /v0/hello` from a valid `app` timed out after 10 s while one bare socket was open, and answered 200 once it closed. Fix: wrap each accepted socket with `do_handshake_on_connect=False` and do the handshake in the request's thread under the 30 s timeout (override `get_request`/`finish_request`).
3. **`refuse_secrets` is bypassed by splitting a secret across appends** (`Rows.verdict` sees only the new body; `FS.handle` append). `POST …/notes.txt/append` with `-----BEGIN PRIVATE ` then `KEY-----` both return 201 and the file holds the header. Fix: on append, scan the last few hundred bytes of the existing file together with the new bytes (the longest shape bounds the window).
4. **Concurrent writes to one path all fail** (`sharness_ai/fs/disk/Disk.py`, `write`). The temporary name is `.sharness-fs-<pid>-<name>.tmp`, the same for every thread of the threaded server; the second writer's `O_EXCL` fails and its cleanup unlinks the first writer's temporary file, whose rename then fails: 8 of 8 concurrent writers failed (`FileExistsError`, `FileNotFoundError`). Fix: a random suffix (`secrets.token_hex(8)`) and unlink only the name this call created. A long file name also overflows 255 bytes once the prefix is added.
5. **A binary file does not read back** (`FS.handle`, read): the content is decoded as UTF-8 with replacement characters, so bytes above 0x7f are lost while `size` reports the true length. Fix: `content_b64` when the bytes are not UTF-8.
6. **Wording on `contain` and `explain`** (`sharness_ai/cli/CLI__Level.py`, `_report_lines`): "held: N rows by the kernel: files, ports, caps; nothing else is reachable" is printed directly above "not held: github.com: held as port 443; the host name is not held", so the screen says nothing else is reachable while every host on 443 is, and UDP and Unix sockets are listed as not covered on the next line. Suggested: "held: N rows by the kernel: files, ports, caps" and, when there are unheld rows, nothing more. Smaller: `L3.site` drops a path silently (`github.com/x` is accepted as `github.com`) though its error text says "no path".

Checked and sound: the edge matrix (a valid `net` certificate is refused on `fs`), the `openat` walk with `O_NOFOLLOW`, keys born 0600 and the CA key destroyed in a `finally`, `contain` running the child with `--expect-hash` on the chain's level-2 hash and removing its temporary policy after the fork returns, `Verdict.clean` on every echoed string.
