The editor plans to release the CLI's `dev` to `main` (R7, which publishes v0.2.0) and to show `sharness-ai` live at an AI event on 29 Oct 2026. website@sharness built a wheel from `dev` at 8210807 and ran it clean on 29 Oct 2026 (Linux 6.18, Landlock ABI 7, as root). It found `doctor` 9/9, `hello` 6/6, and `contain` working. `sharness-ai shell --sites pypi.org` ran as a fresh uid: pypi.org was allowed through `sharness.net`, and example.com, a direct connect to 1.1.1.1 and a write to `/etc` were refused. pytest gave 228 of 229; the one failure was the run's venv under a root-only directory, not the code. Two things stand between `dev` and the release:

1. **The README's status block, before R7.** The README becomes the page on PyPI. Its status block (`README.md` line 46) still says "No SHarness component (launcher, kms, net, fs, bash, llm) is built", and the `components` row says "all seven designed, none built". It should say what [What exists today](../../evidence/status/index.md) says: three MVPs (the levels; `sharness.fs`; `sharness.net` with `sharness-ai shell`, the launcher's first slice), each door a Setting until the launcher gives it its own uid. The pyproject description still lists only the experiments.
2. **`/dev/null` inside `sharness-ai shell`.** `sh -c 'echo x 2>/dev/null'` prints `cannot create /dev/null: Permission denied`: the shell's policy has no write right on `/dev/null`. Most scripts redirect there, so they break, and a live demo would show the error. A write right on `/dev/null`, and read rights on `/dev/zero` and `/dev/urandom`, likely belong in the shell's profile. Not a blocker: the demo script avoids it.

T25 items 3, 5 and 6 stay on T25 and do not block the release; they are listed as known issues on [sharness.fs](../../components/fs/index.md#5-known-issues-as-of-28-oct-2026).

When PyPI shows v0.2.0, website@ switches every install line on the site from `git+…@dev` to `pip install sharness-ai` in one release.
