sharness.ai / the code / playground

Playground: sharness-ai in Pyodide and in Linux

Two runtimes, one page, nothing installed on your machine. On the left, Pyodide: Python compiled to WebAssembly, where pip install sharness-ai installs the CLI and you can hash, check and translate Process Behaviour Policies. Switch to Linux: Alpine with a Landlock kernel, booted by v86 in this tab, where every sharness-ai run is enforced by a real kernel, on a network this page provides, with every packet shown and vetoed in the panel below the terminal. On the right, one policy, hashed by three implementations.

What each tab can show. Pyodide has no kernel and no processes, so run and hello refuse there with exit 126: there is no child to confine, and the CLI says so rather than pretend. In Linux every policy is applied by the shell's sharness-ai to its child: a Boundary for the child, a Setting for the shell, which could have skipped it. The kernel is real; the CPU is emulated, so a command takes seconds. The wheel is the CLI's dev branch, versioned +dev.<commit>; PyPI carries only releases. Built and tested as of 25 Oct 2026. The milestone behind it: Linux in a tab.

The network, seen from outside the guest

The guest's packets have nowhere to go but this page: v86 presents a network card, and the page answers as the router, the DHCP server and the DNS of a fake subnet, turning every HTTP request on port 80 into the browser's own fetch() over TLS. So the page can decode every frame (ARP, DHCP, DNS, ICMP, TCP, HTTP) into the table under the Linux terminal, and it can say no: hosts not on the egress allowlist get a 403 before any fetch() happens. That allowlist is enforced by code the guest cannot reach, root included: a Boundary for everything inside, and the shape of sharness.net in the design, played by the page. Three verdicts to see in one session, as of 25 Oct 2026, each checked by the test:

Type thisDecided byIn the panel
wget -q -O - http://sharness.ai/llms.txtthe page: on the allowlistDNS, TCP :80, HTTP GET … allowed 200; click the row for both sets of headers
wget -q -O - http://example.com/the page: not on the allowlistblocked; the guest sees 403 Forbidden
sharness-ai run --policy policies/p1-agent-session.json -- wget … (TCP 443 only)the kernel, before any packet left the processno TCP or HTTP row at all. The DNS query still appears: Landlock does not see UDP, and here that gap is on screen
sharness-ai run --policy policies/p5-web-fetch.json -- wget … (80 and 443)the kernel allows; the page allowsthe flow, with its 200

Edit the allowlist in the panel and run the first line again. Limits: only HTTP on port 80 is served (the page is the TLS client; there is no TLS passthrough, so https:// from inside the guest is reset), and a host that sends no CORS header fails in the browser, which the guest sees as a 502.

Things to try

  • Pyodide: pip install sharness-ai, then sharness-ai policy translate policies/p1-agent-session.json --to claude-code: the same policy as Claude Code sandbox settings, followed by what that sandbox cannot enforce. Then sharness-ai hello, and read why it refuses.
  • Linux: sharness-ai hello (six probes under a deny-all policy, 6 of 6 when the kernel holds), then the chips: a write refused under P2, port 80 refused under P1, 200 MiB refused under P0's 64 MiB cap, a wrong --expect-hash that runs nothing.
  • Your own policy: edit the JSON on the right, press Hash it in three places, then Use it, and run something under policies/my-policy.json in Linux. Remove /lib from exec and watch every dynamic binary fail to start: the ELF interpreter needs the execute right too.

How it is put together

Installmicropip installs sharness_ai-…+dev.<commit>-py3-none-any.whl from this sitebaked into the initramfs by build_guest.py
Terminala line-oriented terminal that calls sharness_ai.cli.main and captures its outputthe guest's /bin/sh on the serial line (sharness.mode=shell on the kernel command line)
Enforcesnothing: no kernelLandlock files, exec and TCP ports, an empty network namespace, rlimits and cgroups; outside the guest, the page's egress allowlist
Networkthe browser's, for micropip onlyvirtio-net to v86's fetch backend: DHCP, DNS and HTTP on port 80 answered by the page, every frame decoded by netwatch.js
Getting a file inthe Pyodide filesystem, directlybase64 over the serial line, in shell-sized chunks

The code is one ES module, playground.js, in the CLI repository's experiments/browser/, with netwatch.js, the interceptor, beside it, and a headless test that drives both tabs (test_playground.mjs, 17 checks: Pyodide loads and installs, four commands give the expected output, the guest boots to a shell, hello holds 6 of 6, a write is refused, a fetch through the page succeeds, a host off the allowlist is blocked, the kernel refuses under P1 with no packet reaching the page while the DNS query does, P5 succeeds, the three hashes agree). The scripted run of the same guest, without a shell, is the E09 page; what it shows and does not is on Linux in the browser.
