Status: the first standard written, as of 26 Oct 2026. Most of SHarness is a specification, not code: the policy's shape and hash, the manifest and the edges, the protocols of the components, the acceptance test (One standard, many languages). This page is the registry: one row per standard with its version and its test vectors, one row per implementation with its language, where it lives, what it passes and who reviewed it. A row says runnable only with the commit and the test run that make it so. Kept by dev@sharness.

1. How a standard is published here

Each standard has one page with four things: a version of its own (independent of any implementation's); the normative text, a list of musts; the test vectors, as files an implementation's CI fetches from this site (vectors.json lists them, with the expected hash or the reason for refusal); and the registry row of every implementation. The reference implementation (the Python CLI) is the oracle: tools/gen_vectors.py runs every case through it and refuses to publish a vector the oracle disagrees with. A change to a standard is a new version with its own vectors, never a silent edit; the old version's page stays.

What a specification is for SHarness, and the four parts a spec needs before it is more than an Expectation (schema, canonical form and hash, composition, conformance), is pbp@sharness's definition on the PBP on one page §8. The pages here are the second part made concrete, standard by standard; the conformance statement (which probes an enforcer must refuse, how it reports barrier kinds) is pbp@sharness's and is referenced, not restated.

Every implementation's CI runs the vectors twice: the copy vendored in the repository (what the commit was written against) and the copy published here (the standard as it is now), so a change to the standard is seen by every implementation on its next run, and a vendored copy that drifts is seen too.

4. How the doors change the registry

pbp@sharness's rule of 26 Oct 2026, from the editor: the components are doors, named as a tree, sharness.<door>.<target>, where the second name is where the door sends (sharness.fs.s3, sharness.db.sqlite, sharness.net.proxy), every door declares what it accepts and what it emits, and a twin is a target with the real thing's signature. For the registry that means three things. A standard is written per door (its accepts and emits) and its vectors per target, run first against the target's twin. An implementation's row names the targets it carries, with twin or live as a measured fact beside each, never implied by a passing suite. And the module paths the vectors cite are the dotted names, the same in every language: sharness_ai/fs/s3, sharness_ai.db.sqlite, and their equivalents in the Go and JavaScript trees, so the brief on one repository per language carries the tree as the layout of every implementation.

5. What this page does not claim

  • No implementation is a SHarness component. Three languages can hash and check a policy; none can enforce one except Python, and that for a child process, as a Setting for the process that applies it.
  • "Passes" is a test run on one machine on one date, named in the row; it is not a measurement of enforcement.
  • "Reviewed" is a second reader of the code, named; a blank cell means nobody has read it but its author.
