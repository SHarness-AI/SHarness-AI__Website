Status: experiments. No SHarness component is built. What is runnable is listed here with where it runs; what was measured carries its date; everything else is planned. The design these experiments test is on the design pages.

Dinis Cruz's memo of 24 October 2026 sets the method: start with very simple examples, each component done in isolation, as simple, as fast and as slim as possible; then harden; then test. This page is that method as a ladder. Each rung is something a person can run, in the browser, in any Claude session, or on a Linux box, and each says what it shows and what it does not.

The example policies

experiments/policies/ carries two minimal examples and five profiles, P0 to P4, with /work as the workspace. They are the Process Behaviour Policies the ladder is climbing towards, written in the v0 shape so they can be hashed, enforced and translated today:

ProfileWho it is forWritesNetworkCaps
P0 p0-hello-worlda hello worldnonenone64 MiB, 8 processes
P1 p1-agent-sessiona coding agent's session (a Claude Code session, an orchestrator)/work, /tmpTCP 4434 GiB, 512
P2 p2-tool-servera tool or MCP server on stdiononenone512 MiB, 16
P3 p3-newsroom-agentthe sgit.ai newsroom agent: a vault checkout in, articles out/work/outTCP 4431 GiB, 64
P4 p4-sgitthe sgit CLI: the vault checkout and /tmp/work/vault, /tmpTCP 443512 MiB, 16

How they compose: a launcher applies P1 to the agent's session; the session applies P2 to each tool it starts, a Boundary for the tool and a Setting for the session. P3 and P4 are two processes of one workflow with different writes: the agent writes articles, sgit writes the vault, neither can do the other's job. What v0 cannot say yet, in roadmap order: hosts (ports only; the hosts are sharness.net's allowlist), UDP, uids and seccomp, signing, layers composed by intersection.

Run natively on 25 Oct 2026 (the same session as Evidence §9, uid 0, against a stand-in workspace), <span class="asof">as of 25 Oct 2026</span>: P0 refused a 200 MiB allocation under its 64 MiB cap; P1 connected on 443, was refused on 80 and wrote the workspace; P2 was refused every write and the connect; P3 wrote out/ and was refused vault/; P4 ran sgit 0.24.0 (--version, pki list), wrote vault/, was refused out/, connected on 443 and saw its own hash in SHARNESS_AI_POLICY_HASH. In the E09 guest the seven files check and hash to the same values, and P0, P1 and P2 held the same way. One rule they all carry: the ELF interpreter (/lib/ld-musl-*.so.1 on Alpine) must be executable, or nothing dynamic starts.

Running them in a Claude session

The CLI repository carries a skill, sharness-hello, that runs E01 and E04 inside a Claude Code session under the design's safety rules: never touch the orchestrator, never firewall uid 0 or the model API, everything as a child subtree, leave nothing behind. It reports in the site's status words and says, every time, that a policy the session applies to its child does not bind the session.

That is the honest answer to the memo's maybe even a skill (roadmap decision 8): a skill can install the CLI, run the experiments and apply a policy to everything the session starts from then on; it cannot apply one to the session itself. Binding the session needs the launcher above it.

What Claude Code's own sandbox already gives, and what SHarness adds

Claude Code ships a sandbox for shell commands (documented at code.claude.com/docs/en/sandboxing, read 24 Oct 2026): on Linux, bubblewrap for the filesystem, a separate network namespace, and a proxy outside the sandbox that checks each connection's hostname against allowed and denied domains; on macOS, Seatbelt. It is off by default and on with "sandbox": {"enabled": true}. The design pages did not mention it; the research behind this release did, and the comparison is useful because the two agree on the mechanism and differ on exactly the points SHarness is about.

Claude Code sandbox (as documented 24 Oct 2026)SHarness (designed)
What it coversBash, PowerShell and Monitor commands and their childrenevery process, including the orchestrator: enforced at the root of the process tree
Not coveredbuilt-in Read, Edit, Write, WebFetch; hooks; MCP servers; excludedCommands; the harness itselfthe design's "side doors" list is this list; sharness.bash as the only way to run a process is how it closes them
Fileswrites limited to the working directory and a temp dir; reads of most of the machine, credentials includedper-component, per-subcommand read, write and exec lists; the workspace with no execute right; sharness.fs as the only writer
Networka hostname allowlist at a proxy that does not terminate TLS (domain fronting noted as a limit in its own docs)sharness.net is the TLS client, so it sees and verifies the name; endpoint and vault-id allowlists; no redirects, no IP literals
Secretsthe sandbox does not hold or hide them; the model API key stays with the harnesssharness.kms holds them; the harness holds a dummy; sharness.llm adds the real key
Who decidessettings the user (or a managed policy) sets; allowUnsandboxedCommands and the unsandboxed retry are escape hatches by designone manifest hash the person supplies out of band; the launcher refuses anything else; no retry path
Who enforcesthe Claude Code process, for its own childrena launcher above the agent; the platform in the end state

Two conclusions for the design, carried to Agents and LLMs §2 and Policies §9: the sandbox is the natural transparent host for sharness.bash on a laptop today, and its documented limits are a checklist of what the components add. A SHarness policy should be able to generate the sandbox's settings as one of its enforcement layers, the same way it would generate a Kubernetes securityContext.

What is not here

  • No component. Every experiment is a probe or a one-process enforcement; sharness.launcher, .kms, .net, .fs, .bash and .llm are designs.
  • One environment. E04 was measured in one cloud session on one day. A laptop will differ: no root, and on Ubuntu 24.04 an unprivileged user namespace may be refused, so network: "none" falls back to Landlock's TCP rules, which do not cover UDP.
  • The browser mockups compute, they do not enforce. A hash in a browser proves two implementations agree. E09 is different in kind: a real kernel in the tab confines a real process, but the process is the guest's, and nothing in a tab says anything about the host.

Sources: experiments/README.md in the CLI repository; A secure harness for agents; the Claude Code documentation on sandboxing, permissions and hooks, read 24 Oct 2026.
