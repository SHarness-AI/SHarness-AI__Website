Languages

Status: a recommendation, as of 25 Oct 2026, for roadmap decision 11. What each part of SHarness is written in, what it should be written in, and why. The rule behind every row: reuse what Linux and the standard library already have before writing anything, and keep each piece small enough to read in one sitting.

What is written, and in what

PartLanguage todayWhy
the CLI and experiments E01 to E04Python 3.11+, standard library onlyfast to iterate; ctypes reaches Landlock, unshare and memfd_secret without a C extension; sgit, the first harnessed app, is Python, so the same team reads both; the design's measurements were taken in Python
the browser mockupsJavaScript in the page, no framework; WebCrypto for SHA-256the only language a browser runs; the point of the policy-hash mockup is a second implementation that must agree with the Python one
the storyboardsJSON data, drawn by the storyboards.sgit.ai kit (JavaScript, pinned release)data, not code
this site's toolsPython standard library (generators) and Node (the gate, the kit's validator)no build dependencies; the same pattern as the other sites in the network

What each component should be written in

ComponentRecommendationReasonWhen
sharness.launcherPython first, a static binary later if a platform needs oneit is configuration of things the kernel already does (uids, namespaces, cgroups, certificates); the design's target is ≤ 400 lines; Python's ssl and the cryptography package make the session CA a few dozen linesE06 onwards
sharness.net, sharness.fs, sharness.llmPython, standard library plus cryptography where sealing is neededeach is a small server over mutual TLS with a JSON schema; Python's ssl module does TLS 1.3 with client certificates; the measured handshake (3.2 ms) was Python'sE05, E07
sharness.kmsPython v0 (E08), then Rustthe KMS is the one place where memory hygiene decides the security: the design already notes that Python cannot guarantee erasure, that OpenSSL copies the key into its own heap, and that scrubbing bytes is best effort. A Rust KMS with zeroising types and memfd_secret through a thin syscall layer removes a class of caveats. v0 in Python first, to settle the protocolafter E08
sharness.bash (the server)Pythonit is a launcher for one command at a time: cgroup, namespaces, uid, Landlock, exec, filterE06
sharness-bash-clienta small static binary: Rust or Gothe design requires it: the orchestrator's execute allowlist must not include an interpreter, and a static binary needs none. Rust for size and no runtime; Go if the team prefers itE06
the seccomp filtersdata (a syscall list per component in the policy), compiled to BPF by a few lines of Python; libseccomp if available, raw BPF through ctypes if notthe filter is part of the policy and hashed with itthe next rows of Containment
the policy languageJSON (canonical, hashed); YAML only for reading on the sitetwo implementations already agree on the bytes; a policy language is explicitly not wanted (Components)now
the Messages API front of sharness.llmPython, then whatever the platform wants when it runs the component as a servicethe API is HTTP and JSON; nothing language-specificE07
the browser experiments (a Linux kernel in a tab)JavaScript and WebAssembly around an existing emulator; the kernel and rootfs built with the normal Linux toolchaina page on this is being researchedplanned

Two rules that follow

  1. Python until a caveat says otherwise. Every component starts in Python because the experiments do and because the design's own figures were measured there. A component moves to Rust only for a stated reason (memory hygiene in the KMS; a static binary for the bash client), recorded on the roadmap.
  2. No runtime dependencies in the CLI beyond cryptography for the components that seal and sign. The experiments stay standard-library only so a Claude session can install and run them anywhere Python is.

Reference implementations in several languages (proposed, 25 Oct 2026)

Dinis Cruz's brief of 25 Oct 2026 extends decision 11 from "which language for each component" to "reference implementations of each component in several languages, against one standard per component, with test vectors and a reviewed registry". The developer agent's map of that is the article One standard, many languages: what in each component is a specification (the policy's shape and hash, the manifest and the edges, the KMS, net, fs, llm and bash protocols, hello's six expectations) and what is an implementation (reaching the kernel, serving mutual TLS, holding a secret), then a component-by-language matrix.

LanguageCarriesProposed roleOrder
Pythonthe standards, the servers (ssl), the kernel (ctypes); not a static binarythe first implementation, and the one the measurements are taken in; sharness.kms v0 to settle the protocoltoday
JavaScript in Nodethe standards, the servers (tls); the kernel only through a helper binarynet, fs and llm where MCP servers and agent loops are written; run delegatesfirst
JavaScript in the browserthe standards (WebCrypto); no sockets, no kernelthe hash and check with nothing installed (runnable today for the hash); CSP as a translate targetwith Node, one package
Goall four kinds, with TLS and a static build in its standard library and Landlock in x/sys/unix; not the KMS (the collector may copy a secret)the second complete implementation; the bash client; the first non-Python footprintsecond
Rustall four kinds; rustls pinned for the servers; no collector, so a secret can be zeroed in placesharness.kms after E08 and the bash client, as this page already recommendsthird
Java, .NETthe standards and the servers; the kernel through their standard FFI; heavy runtimesharnessed-app SDKs and policy tooling, on interest; translate --to kubernetes as their first enforcerlater
C, assemblythe kernel calls and nothing elsea run in a few hundred lines as the floor, for teaching and for the footprint comparisonlater

The rules above still hold: Python until a caveat says otherwise, and no runtime dependencies beyond a stated, pinned exception. What changes is that the exception list grows by one per language (rustls in Rust; nothing in Go or Node), and that each implementation must pass the same test vectors (the seven example policies and their hashes, hello's six expectations) before it enters the registry. The decision remains Dinis's; the request is R8.

What this does not decide

Whether the platform-provided versions of the components (topology E) share any code with these; the design says only that the protocol is the same. And nothing here is a commitment of sgit's maintainers about sgit's own language, which is Python today.
