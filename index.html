★ GitHub
Open source · Python, standard library only · enforced by the Linux kernel

Give every process an AI agent starts
a policy the kernel enforces.

SHarness runs an agent's tools as small processes, each under a Process Behaviour Policy: what it may read, write, run and connect to, named by one hash the person supplies. A tricked agent cannot widen it, because the kernel was told before the process started. Today that is a CLI you can run on Linux, a kernel that boots in your browser to prove it, and a design for the launcher that binds the agent itself.

The one idea

A policy you can hash, a kernel that enforces it on the process, and a launcher above the agent that starts only what the hash names. The first two run today; the third is the design.

1Write what one process may doFiles it may read, write and run; ports it may connect to; how much memory and how many processes. A few lines of JSON. Nothing else is allowed.
2Hash it: that is its nameCanonical JSON, SHA-256. The person supplies the hash from outside the agent, so a prompt-injected agent cannot widen the policy without changing the name.
3The kernel enforces itLandlock rules per path and port, a network namespace, rlimits and cgroups, applied before execve. The process and everything it starts can only lose rights.
4The caveat, every timeApplied by a process to its own child it is a Boundary for the child and only a Setting for the process. The launcher above the agent, which makes it a Boundary for the agent too, is the design.

Three ways in. None needs a component that does not exist yet; each runs the experiments that do.

In your browser · nothing to install

The playground

Two terminals in one tab. Pyodide: Python in WebAssembly, where pip install sharness-ai gives you policy hash, check and translate. Linux: Alpine with a Landlock kernel, where every sharness-ai run is enforced. One policy, hashed three ways.

$ pip install sharness-ai
sharness:/work# sharness-ai hello
result      6/6 held

In a terminal

Standard library only, so the install is one line. probe prints what a process here can do before any policy; hello checks that a policy holds; run puts any command under one.

$ pip install git+https://github.com/SHarness-AI/SHarness-AI__CLI@dev
$ sharness-ai probe
$ sharness-ai hello
$ sharness-ai run --policy p2-tool-server.json -- my-tool

Who it is for

Three people, one policy format. The policy is the centre; every enforcer, ours included, is a target for it.

You run coding agents

Put the agent's tools under a policy today

A Claude Code session, an orchestrator, a script that calls tools: start each tool with sharness-ai run --policy … and the kernel holds it to the file, port and memory limits you wrote. P1 and P2 are the profiles to start from. The caveat applies: the agent's own process is bound only by a launcher above it.

The example policies → You ship a tool or an MCP server

Ship the policy with the tool

Write the policy your tool needs, hash it, and publish both. Whoever runs your tool runs it under that hash, and sees exactly what you asked for: a read-only workspace, one port, a memory cap. A tool that needs less is easier to trust.

One policy, every enforcer

sharness-ai policy translate writes the same policy as a bubblewrap command, a docker run, a Claude Code sandbox setting or a Kubernetes Pod and NetworkPolicy, and lists what each of those cannot enforce. The enforceability matrix is that list, row by row.

Help us measure it

A claim that the kernel enforces a policy is only as good as the kernels it was checked on. So far that is one cloud session, one browser and one emulator. Your machine is the next row. Run the acceptance test and paste what it said:
$ pip install git+https://github.com/SHarness-AI/SHarness-AI__CLI@dev
$ sharness-ai hello --json
then open a hello report on GitHub (two fields: the JSON, and anything odd). Every report goes on the machines page with its kernel, Landlock ABI and result, including the ones that did not hold: a refusal that did not happen is the most useful thing you can send. Nothing in the JSON identifies you; probe prints the names of proxy variables, never their values.

The operating system a process sees

Bound everything a process can do and what is left is its policy: no filesystem of its own to write, no network stack, no key, no shell, no model API. In their place, five doors, each a small REST service on loopback with its own uid and policy, and the bootstrap that started them. Designed, not built; the locks under them run today.

start here

sharness.bash: the shell, as a service

Each command in a fresh sandbox under a profile, output filtered. Where every lock is applied at once, and the first to build: once a command can only run through this door, the other doors are the only ways out.

Read → pick one: worth it alone

sharness.net: the only network client

The TLS client, so the hostname is seen and verified; host, endpoint and id allowlists; no redirects elsewhere, no IP literals; a log of every request. Its allowlist already runs in the playground, outside a guest.

Read → secrets

sharness.kms: where a secret lives

Opens sealed things, derives what the caller needs, re-seals it to a one-time key. Never returns a clear key; frozen between calls; its page unreadable even by root.

Read → files

sharness.fs: the only writer

Writes under the root it owns, inside the rules, and refuses anything that parses as a clear key, a private key or a token.

Read → the model

sharness.llm: the only model client

The Messages API, unchanged, with the key out of the agent's process, the tool list pinned, and a secret filter on every tool result.

Read → the bootstrap

sharness.launcher and the manifest

Refuses unless the manifest hashes to what the person supplied; one uid per component; a session CA. Who runs it decides what the locks are.

What this site claims, and how

The same distinction runs through every page. Every number is labelled; nothing is presented as built.

LabelMeans
MeasuredProbed or timed in a named environment on a named date, with the method on Evidence. For example: hello 6 of 6 in five places; a mutual TLS handshake between components ≈ 3.2 ms; a memfd_secret page unreadable even by root.
RunnableThe code is in the repository and its tests pass: probe, policy hash, check, translate, run, hello, the browser bench, the playground.
Designed / proposedHow SHarness would work: the components, the KMS protocol, the policy layers, .llm, .bash, the deployment topologies.
Never claimedThat any component is built or released; protection against root or kernel compromise; anything about any platform's plans; that a schema bounds intent (it bounds shape).
